桌面端读起来正好的字号，到了手机上会变得难以忍受。这不是第一次遇到，但这次的解决方式值得记一笔。

## 症状

文章详情页的 `h2` 在桌面端是 48.8px，配 720px 的阅读栏很稳。手机上的阅读栏只有 358px，`h2` 却还有 43.9px。

问题不在绝对数字，而在比例：标题一直是正文的 2.44 倍，正文在 720px 处从 20px 掉到 18px，标题只跟着缩了 10%，栏宽却缩了一半。

## 先分清是谁的配置

站点里有两套字号：

- `@ezhana/design-theme-cerulean` 提供 `--font-size-h1…h4`，其中 `h2` 是 20–24px；
- `@ezhana/typography-editorial` 用自己的 `--ez-editorial-heading-scale`，按 1.25 的模数从正文字号累乘出标题。

文章正文只吃第二套。Cerulean 的 `h2` 是给界面外壳准备的，接到文章里会比正文还小。所以这不是改一个主题 token 的事，而是预设需要为窄屏补一条规则。

## 更麻烦的是作用域

最初 `.ez-editorial` 包住了整篇文章：封面、标题、日期、正文。看起来省事，代价是标题也成了预设的 `h1`。想只调正文标题，就必须动全局的 `scale`。

于是先做了一件与字号无关的事：把 `.ez-editorial` 收窄到只包渲染后的正文。

- 文章标题交给站点自己的字号角色，不再由预设的 `h1` 决定；
- 封面圆角回到 `--radius-surface`；
- 关于页不再复用文章布局，`ink-redacted` 从博客样式移到组件层；
- 友链组件自己负责标题和间距。

顺带踩了一个坑：用 `[&_a]:underline` 这类容器级变体给页面文案上样式，会连友链卡片一起加下划线——选择器是 `.container a`，优先级高于卡片自己的 `no-underline`。后来改成显式的 `.copy-link`，只作用在被标记的链接上。

## 先删补丁，再等上游

收窄作用域之后，手机端的 `h2` 仍然偏大。当时用媒体查询把 `scale` 压到 1.18 / 1.14，但这是补丁，不是修复：预设本身没有窄屏方案。

补丁后来被删掉了。那段时间手机上的 `h2` 比文章标题还大——接受这个中间态，把问题留给预设。

## 0.2.0 之后

预设的新版本给了两样东西：每级标题自己的 `clamp()` 阶梯，以及 `.not-prose` 逃生口。`scale` 是无单位数，乘 `vw` 会得到长度平方，所以新方案改成「紧凑阶梯 + 视口增量」，标题因此连续变化，不再依赖正文的 720px 断点。

升级后实测，390px 下 `h2` 从 43.9px 降到 35.97px。问题反过来出现了：站点 `--font-size-h1` 在 390px 也是 36px，标题和 `h2` 撞在一起；768px 下 `h2`（43.8px）甚至反超标题（40.9px）。

文章标题是页面自己的东西，应该用更大的角色。改用 `display`（40–64px）后，标题在 390 / 768 / 1280 分别是 40 / 48.8 / 61.1px，层级恢复。

最后再调了一档：`--ez-editorial-heading-scale-compact` 从 1.15 降到 1.10。390px 的 `h2` 到 30.84px，`h2` 与正文的比例从 2 倍落到 1.71 倍。代价是桌面端也小了一点：1280px 的 `h2` 从 48.83px 变成 44px，完整的 1.25 阶梯要到约 1700px 才追平。

## 记下三件事

1. 容器式后代选择器会穿透组件。样式要么显式标记，要么接受它是一套作用域。
2. 补丁要写清删除条件，否则会变成事实上的设计。
3. 字号别靠目测。用无头浏览器量一遍，`clamp()` 里的 `em` 是父元素的字号，不是自己的。
